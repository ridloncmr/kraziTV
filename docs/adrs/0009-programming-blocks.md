# 0009 Programming Blocks Between Channels and Schedule Entries

## Status

Accepted

## Context

kraziTV's end state is a TV programming scheduler. A user assigns collections to
a channel, kraziBrain generates programming automatically, and the user can then
open any stretch of that programming, such as a four-hour Office marathon, to
change how it plays, shorten it, or replace what follows.

The accepted MVP specs model programming as two fields on the channel:
`mediaCollectionId` and `playbackMode`. Schedule generation turns those fields
directly into schedule entries. That shape cannot express the end state:

- A channel can play only one collection in one mode. "The Office in order,
  Workaholics shuffled" on one channel is impossible.
- There is no persisted unit of programming a user can open and edit.
- Random selection derives from one channel-wide seed and the channel-wide
  sequence number. Once several collections share a channel, each one's
  selections would depend on what the others aired, and editing one stretch
  would reshuffle the rest.
- Chronological progress is implicitly channel-wide. After a Workaholics
  stretch, The Office should resume at its next episode rather than at a
  position derived from unrelated airings.

Moving playback mode onto the media collection does not help. A collection
answers what can be selected (ADR 0006), so the same collection should be
playable in order on one channel and shuffled on another, and a channel would
still be limited to a single collection.

The MVP must stay small, but storing programming in the channel-field shape
would force table rewrites and regeneration-policy changes when the scheduler
grows.

## Decision

kraziTV introduces the **programming block** as the persisted unit of
programming between a channel and its schedule entries.

```text
Catalog -> Media collections -> Programming blocks -> Schedule entries -> Playout timeline
   |                            (per channel; what      (guide authority,
   `---- single media item ---> to play and how)        ADR 0003)
```

- A **channel** is a broadcast identity only: number, name, and enabled state.
  It carries no collection or playback-mode fields.
- A **programming block** belongs to one channel and selects exactly one
  source: a media collection or a single media item. A single movie or special
  does not need a one-item collection. A collection source also selects a
  playback mode; playback mode belongs to the block, not to the channel or the
  collection. A single-item source has no playback mode and no playback
  progress.
- **Schedule entries** are materialized from programming blocks. Each entry
  records the programming block that produced it. Entries remain the guide
  authority, and every ADR 0003 policy (horizon, regeneration boundary, gap
  repair, transactional mutation, schedule revision) applies unchanged.
- **Playback progress is tracked per channel and collection**, not per channel.
  Chronological position and the random selection index advance only when that
  collection airs on that channel, so separate stretches of the same collection
  continue where the last one left off. Each schedule entry records the
  collection position or selection index it consumed, so regeneration restores
  progress from the entries it keeps instead of replaying process state.
- Random selection stays deterministic: it derives from a seed scoped to the
  channel and collection plus that collection's selection index.
- How a collection was built (manually today; automatically or by rule later)
  is invisible to blocks and channels. A collection is always consumed as an
  ordered list of media items.

### MVP Constraint

The MVP allows exactly one programming block per channel. That block covers all
time and loops its source, which reproduces today's specified behavior in the
new shape. A channel with no block, or whose block's source has no schedulable
media, is unschedulable and reports so instead of producing entries. The block
source is persisted as an explicit either/or (collection or media item) so
further source kinds can be added without reshaping existing rows.

### Planned Extension Path

Each step adds data and logic without rewriting the MVP model:

1. Metadata enrichment after probe, through the catalog scanner's existing
   post-probe extension seam.
2. Automatic and rule-based collections that populate the same ordered
   membership.
3. Several blocks per channel, generated by **kraziPlan**, the automatic
   programming generator inside kraziBrain, from the collections assigned to
   the channel. kraziPlan writes programming blocks; it never writes schedule
   entries directly.
4. Clock-anchored blocks on a guide grid, together with filler.
5. User overrides: editing a block's mode or length and placing media or blocks
   by hand. Saved overrides take precedence over generated blocks; regenerating
   an edited block replaces only its own future entries and never the airing
   one.

## Alternatives Considered

| Option                                       | Outcome                                                                                       |
| -------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Keep collection and mode on the channel      | Rejected. Cannot mix collections or modes and leaves no editable unit of programming.         |
| Put playback mode on the media collection    | Rejected. Couples "what" with "how", forces duplicate collections, and keeps one collection.  |
| Build kraziPlan and multiple blocks into MVP | Deferred. Adds alternation, grid, and override policy before the core playout loop is proven. |

## Consequences

- Spec 0003 narrows to channel identity, the channel lifecycle including
  administrative runtime shutdown, and media collections.
- Spec 0004 owns the single MVP programming block, per-channel-and-collection
  playback progress, and the programming block reference on schedule entries.
  Its channel-wide seed and sequence-derived selection change accordingly; the
  channel-wide `sequenceNumber` remains for ordering and uniqueness.
- Spec 0008 moves source (collection or media item) and playback-mode
  selection from the channel form to the channel's programming block.
- The glossary gains **Programming block**, redefines **Playback mode** as a
  block setting, and lists **kraziPlan** and **Automatic collection** as
  planned terms.
- ADR 0003 is unchanged. ADR 0006 is refined: programming blocks, rather than
  channels, reference media collections.
- The MVP carries one extra table and one extra form step compared with channel
  fields, in exchange for avoiding a schema and regeneration-policy rewrite when
  multi-block programming arrives.
